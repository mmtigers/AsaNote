# repo-survey — リポジトリ調査(読み取り専用)

ファイルは変更しない。外部への書き込みもしない。調査対象は、現在のリポジトリ(引数があればそのサブディレクトリ)だけ。`node_modules` や生成物は辿らない。

## 手順
対象: 引数でサブディレクトリが渡されたらそれ、無ければリポジトリ全体。README/docs が無い場所は、上位のものを読む。モノレポは、ルート `package.json` の `workspaces` で各パッケージを列挙する。

1. 状態: `git status -sb`、ブランチ、直近のコミット数件。未コミットの変更があれば報告に含める(触らない)。
2. 指示書: `CLAUDE.md` / `AGENTS.md` / `README` / `docs/` を先に読む。**書かれた規約は調査より優先して従う**(例: フレームワークの版が訓練知識と違うと警告があれば、該当ドキュメントを先に読む)。
3. 構成: ルートの `package.json`(workspaces・scripts)、各パッケージの `package.json`、`.nvmrc`、設定ファイル、CI(`.github/workflows/`)を読む。
4. エントリーポイントと主要機能: ルーティング・API・バッチ・DB スキーマのうち、このリポジトリに存在するものを `Glob`/`Grep` で特定する。ファイルを丸ごと読まず、必要な箇所だけ読む。
5. データフロー: 入力 → 処理 → 保存 → 表示/通知を、実際の import / 呼び出しをたどって1本ずつ確認する(推測で書かない)。
6. テスト・依存: テストの種類と置き場所、実行コマンド、CI が実行する順序。依存は直接依存のみ(古い/重複/未使用の疑いは「疑い」と明記)。
7. 技術的負債: `TODO|FIXME|HACK`、巨大ファイル、テストのない領域、ドキュメントと実装のずれ。

## 報告の形式
- 結論ごとに根拠を `path/to/file.ts:42` で付ける。**確認できなかったことは「未確認」と書く**。
- 順序: 概要(3行) → 構成表 → 技術スタック → エントリーポイント → データフロー → テスト/CI → 技術的負債(影響度順) → 未確認事項。
- 長くなる場合は要点を先に書き、詳細は表にする。
