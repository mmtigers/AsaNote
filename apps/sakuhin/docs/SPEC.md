# さくひんノート 〜おうちの美術館〜 要件定義書 v0.3

子どもが幼稚園・保育園・小学校で作って持ち帰った絵や工作を、写真に撮って「収蔵」し、
額縁に入れて飾っているような見た目で見返せる、家族向けのスマホアプリ(PWA)。

> 状態: v0.3(2026-11-28)。コンセプト・MVP の範囲・DB の構成と権限はオーナーと合意済み。
> §12 の残りの未確定事項を決めてから実装に入る。実装と食い違う点を見つけたら、この文書を直す。
>
> 改訂履歴
> - v0.1(2026-11-28): 初版。名前・使う人・MVP の範囲・言葉づかいをオーナーと合意した(§11)。
> - v0.2(2026-11-28): DB の共有・誕生日の置き場所(共通の `children` 表)・元の写真を残さないことを決めた(§11 D7〜D9)。
>   `children` の更新・削除の権限と、子どもの削除時の作品の扱いを未確定事項に加えた(§12 A4・A5)。
> - v0.3(2026-11-28): 子どもの情報は家族の誰でも編集できる・作品がある子どもは削除できない、を決めた(§11 D10・D11)。

## 1. 目的と前提

### 1.1 解決したいこと

- 子どもが作ってきた作品は、全部を飾ったり保管したりするのが難しい。でも捨てるのは罪悪感がある。
- 写真に撮ってから手放したいが、スマホの写真フォルダでは日々の写真に**埋もれて**、見返さなくなる。

### 1.2 コンセプト

**「撮って、飾って、安心して手放せる。おうちの小さな美術館」**

- 作品を「写真」ではなく「作品」として残す(額縁・タイトル・作者・制作時の年齢つき)。
- 収蔵したら、実物は手放してよいと思える体験にする(§5.6)。
- 子どもごとの「〇〇ちゃん美術館」に、学年ごとの部屋で並べ、あとから見返したくなる場所にする。

### 1.3 前提

- 使う人は**親だけ**(夫婦・家族で共有する)。子ども本人や祖父母が使うことは想定しない。
- アプリは作品を評価しない(上手・下手の判定、ランキングなどはしない)。
- 自動通知・プッシュ通知は MVP の対象外。

## 2. 利用者と権限

| 役割 | できること |
|---|---|
| 親(家族のメンバー) | 子どもの登録・編集、作品の収蔵・閲覧・編集・削除、家族への招待 |

- 同じ家族(グループ)のメンバーは、全員が同じ権限を持つ(あさノート・よるノートと同じ考え方)。
- 権限は**サーバー(データベースの RLS・Storage のポリシー)側で検証する**。画面の出し分けだけに頼らない。
- 未認証の第三者は、作品の情報・写真にアクセスできない(写真は非公開のストレージに置く。§8)。

## 3. 言葉づかい(美術館の言葉)

画面の文言は、美術館に見立てた次の言葉で統一する。雰囲気を出しつつ、わかりにくくならない範囲にとどめる。

| 一般的な言い方 | このアプリの言葉 | 使いどころ |
|---|---|---|
| 作品を登録する | **収蔵する** | 登録のボタン・完了の案内 |
| 子どもごとの一覧 | **〇〇ちゃん美術館** | 子どもごとのトップ。館の名前は変えられる(§5.1) |
| 年度ごとの区切り | **〇〇の部屋**(例: 年中の部屋、1年生の部屋) | 美術館の中の区切り(§5.4) |
| 作品の説明 | **キャプション** | 作品の詳細画面の下に出す説明(§5.5) |
| お気に入り | **常設展** | 特に好きな作品だけを集めた部屋(§5.7) |
| 実物も取っておく印 | **実物保管** | 実物を手元に残す作品の印(§5.6) |

- 「館長」のように利用者を呼ぶ言葉は使わない。
- 説明が要る言葉(「収蔵」「常設展」など)は、初めて使う場面で短い補足を添える(例: 「常設展 ― お気に入りの作品を集めた部屋」)。

## 4. 子どもの登録

| 項目 | 必須 | 内容 |
|---|---|---|
| 名前 | ○ | 1〜50文字。あさノート・よるノートと同じ子ども(共通の `children` 表。§9) |
| 誕生日 | 任意 | 制作時の年齢と、部屋(学年)の自動判定に使う。共通の `children` 表に持つ(§9.2) |
| 館の名前 | 任意 | 既定は「〇〇ちゃん美術館」(〇〇は名前)。自由に変えられる(例: 「HANA MUSEUM」) |

- 誕生日が無い子どもも登録できる。その場合、年齢は表示せず、部屋は年度で区切る(§5.4)。
- 子どもは複数人を登録できる。1人だけの家庭では、子どもを選ぶ操作を省く。

## 5. 機能(MVP)

### 5.1 美術館(ホーム)

- 子どもごとに「〇〇ちゃん美術館」がある。子どもが複数いる場合は、ホームで館を切り替える。
- 館のトップには、部屋(§5.4)の一覧と、常設展(§5.7)への入口を出す。
- 新しい順に、最近収蔵した作品を数点見せる。
- 作品がまだ無い館では、収蔵への案内を出す。

### 5.2 収蔵の流れ

1. **写真を用意する**: その場で撮影する、または端末の写真から選ぶ。
2. **四隅を合わせる(手動の補正)**: 写真の上に4つの点を出し、指で作品の四隅に合わせる。
   合わせた四角形を長方形に引き伸ばして、傾き・台形のゆがみを直す(射影変換)。
   - 点の初期位置は、写真の内側に少し余白を取った長方形とする(自動の検出はしない)。
   - 点を動かしている間は、指の位置を拡大して表示する(指で隠れて合わせにくいため)。
   - 補正しない(元の写真のまま使う)こともできる。立体の工作などのため。
   - 90度ずつの回転ができる。
   - 補正後の縦横比は、合わせた四角形の辺の長さから求める。用紙の規格(A4・八つ切りなど)への合わせ込みは MVP ではしない。
3. **作品の情報を入れる**(§5.3)。
4. **収蔵する**: 保存に成功したら、完了の案内を出す(§5.6)。

- 補正した画像は、端末で長い辺 1600px 以内の JPEG にしてから送る。位置情報などの撮影情報は付けない
  (おやノートの `imageResize` と同じ方針。§8)。
- 一覧用に、小さい画像(サムネイル)も端末で作って送る(§8)。

### 5.3 作品の情報

| 項目 | 必須 | 内容 |
|---|---|---|
| 作者(子ども) | ○ | 子どもが1人なら自動で決まる |
| 制作日 | ○ | 既定は今日。端末の写真から選んだ場合は、撮影日を既定にする(読み取れれば)。日単位で変えられる |
| タイトル | 任意 | 最大50文字。無ければ「無題」と表示する |
| 種類 | ○ | 絵 / 工作 / 書写・文字 / その他(既定は「絵」)。選択肢は1か所の定義に集約し、後から変えられるようにする |
| ひとことメモ | 任意 | 最大200文字。子どもが話していたこと、作った場所(園・学校の行事など)など |
| 額縁 | ○ | §6 の種類から選ぶ。既定は自動(§6) |
| 常設展 | 任意 | オン / オフ(既定はオフ) |
| 実物保管 | 任意 | オン / オフ(既定はオフ) |

- 制作時の年齢は、誕生日と制作日から自動で求める(「4歳3か月」の形)。保存はしない(誕生日を直せば表示も変わる)。
- 1つの作品に付ける写真は1枚(MVP)。

### 5.4 部屋(学年ごとの区切り)

- 作品は、制作日の**年度(4月〜翌年3月)**で部屋に分ける。
- 誕生日がある子どもは、日本の学年の決まり(4月2日〜翌年4月1日生まれが同じ学年)で、部屋の名前を自動で決める。

| 部屋の名前 | その年度の4月1日時点の年齢 |
|---|---|
| 0歳児の部屋 〜 2歳児の部屋 | 0〜2歳 |
| 年少の部屋 / 年中の部屋 / 年長の部屋 | 3 / 4 / 5歳 |
| 1年生の部屋 〜 6年生の部屋 | 6〜11歳 |
| 〇〇年度の部屋 | 12歳以上(中学生以降。MVP では学年名を付けない) |

- 誕生日が無い子どもは、すべて「〇〇年度の部屋」とする。
- 保育園・幼稚園の呼び方の違い(「年少」「3歳児クラス」など)は、MVP では上の表に固定する。
- 部屋の中は、制作日の新しい順に並べる(同じ日なら収蔵の新しい順)。

### 5.5 作品の詳細とキャプション

- 作品を大きく表示する。背景は暗めにし、作品を照らしているように見せる。
- 作品の下に、美術館のキャプション風に情報を出す。

```
『ママとうさぎ』
はな(4歳3か月)
絵 ― 2026年11月28日
年中の部屋
「うさぎがママをおむかえにきたところ」
```

- 拡大(ピンチ)して細部を見られる。
- 同じ部屋の前後の作品へ、左右のスワイプで移れる。
- 詳細画面から、情報の編集・額縁の変更・削除ができる。削除の前に確認する。

### 5.6 収蔵の完了と「手放す」体験

- 収蔵に成功したら、次の案内を出す。
  - 実物保管がオフ: 「収蔵しました。〇〇ちゃん美術館に飾られています。実物は手放しても大丈夫です」
  - 実物保管がオン: 「収蔵しました。実物も大切に保管しましょう」
- 案内は、**サーバーへの保存の成功を確かめてから**出す。保存に失敗したときは案内を出さず、入力を残したまま再試行できる
  (保存できていないのに「手放しても大丈夫」と伝えないため。§7)。
- 完了の画面から「続けて収蔵する」(§5.8)と「作品を見る」を選べる。
- 実物保管の作品は、一覧で印を付け、絞り込めるようにする(どれを手元に残したか、あとで確かめられるように)。

### 5.7 常設展

- 常設展をオンにした作品だけを、年度を問わず集めた部屋。子どもごとにある。
- 並びは制作日の新しい順。

### 5.8 続けて収蔵する

- 学期末などにまとめて持ち帰った作品を、テンポよく収蔵するためのモード。
- 1点を収蔵したら、すぐ次の撮影に移る。作者・制作日・種類は前の作品の値を引き継ぐ。
- 撮影 → 四隅合わせ → (必要なら情報の修正)→ 収蔵、をくり返す。タイトルなどは後から詳細画面で入れられる。

### 5.9 家族で共有

- 家族(グループ)を作り、招待コードでパートナーなどを招く。同じ家族のメンバーは、同じ美術館を見て、収蔵・編集できる。
- 仕組みは、あさノート・よるノートのグループ(`groups` / `group_members` / `group_invites`)と同じ(§9)。

## 6. 額縁と見た目

### 6.1 額縁の種類(初期案)

| 額縁 | 見た目 |
|---|---|
| 木の額(ナチュラル) | 明るい木の枠 + 白いマット。**既定** |
| 白い額 | 細い白の枠 + 白いマット。すっきり |
| 黒い額 | 細い黒の枠 + 白いマット。写真や書写に合う |
| 金の額 | 装飾のある金色の枠。名画風 |
| カラフル | 子どもらしい明るい色の枠 |

- 額縁は、画像に焼き込まず、**表示のときに CSS などで付ける**(後から変えられ、保存する画像が増えないように)。
- 「自動」の場合は、種類で決める(絵・工作・その他 → 木の額、書写・文字 → 黒い額)。
- 額縁は作品の縦横比に合わせる(縦長・横長・正方形が混ざってよい)。
- 工作など補正しない写真も、同じ額に入れる(写真ごと額に入れたように見せる)。

### 6.2 一覧(壁に飾った見た目)

- 背景は美術館の壁のような落ち着いた色(生成り・薄いグレー)にする。
- 作品を額に入れて、壁に並べたように見せる。縦長と横長が混ざっても、すき間が目立たないように並べる(高さをそろえて詰める、など)。
- スマホの縦画面で、1行に2〜3点を基本にする。
- 一覧にはサムネイルを使い、表示を軽くする。
- ダークモードでは、壁を暗い色にする。

## 7. 保存と通信

- 作品の情報と画像は、**サーバーへの保存が成功して初めて「収蔵」とする**。
- 通信できないときは収蔵できない。入力途中の内容(補正後の画像を含む)は端末内に残し、通信が戻ったら再試行できる。
- 一度見た作品の一覧(サムネイル)は端末内にも持ち、通信できないときも見られるようにすることを目標にする(§12 B3)。
- 同じ作品が二重に収蔵されないようにする(作品の id を端末で決めて送り、再試行しても同じ行になるようにする)。

## 8. 写真の保存

- 写真は Supabase Storage の**非公開のバケット**に置き、表示には有効期限の短い署名付き URL を使う(おやノートと同じ方式)。
- 置き場所のパスは家族(グループ)単位で分け、Storage のポリシーで「同じ家族のメンバーだけ」読める・書けるようにする。
- 1つの作品につき、次の2つを保存する。

| 画像 | 大きさ | 用途 |
|---|---|---|
| 本体 | 長い辺 1600px 以内の JPEG(品質 0.85 程度。1点 300〜500KB 程度の見込み) | 詳細画面 |
| サムネイル | 長い辺 400px 程度の JPEG(1点 30〜50KB 程度の見込み) | 一覧 |

- 補正前の元の写真は保存しない(容量を抑えるため。§11 D9)。補正をやり直したい場合は、作品を収蔵し直す。
- 容量の見積もり: 子ども2人 × 年150点 = 年300点 → 1家族で年 100〜170MB 程度。

## 9. 構成と既存アプリとの関係

| 項目 | 方針 |
|---|---|
| リポジトリ | このモノレポに `apps/sakuhin/` を追加する |
| フロントエンド | あさノート・よるノートと同じ Next.js(App Router)・TypeScript・Tailwind。共通コード `packages/core` を流用する |
| データベース・認証・写真 | あさノート・よるノートと**同じ Supabase プロジェクトを共有**する(§11 D7)。ログインも同じ。写真は同じプロジェクトの Storage に、さくひんノート用のバケットを作る |
| 配信 | さくひんノート専用の Vercel プロジェクト(Root Directory `apps/sakuhin`) |
| スマホ対応 | PWA(ホーム画面に追加して使う)。カメラはブラウザの撮影(`<input type="file" accept="image/*" capture>`)を使う |

### 9.1 流用するもの

- グループ・招待・子ども(`groups` / `group_members` / `group_invites` / `children`)。あさノート・よるノートで登録した子どもがそのまま使える。
- 画像の縮小(おやノートの `imageResize`)。共通で使うなら `packages/core` への移動を検討する(core を変えると、全アプリで版上げが要る。`docs/MONOREPO.md`)。
- ログイン・更新履歴・エラー画面などの共通部品(`packages/core`)。

### 9.2 データ(案)

#### 共通の表への変更

| 表 | 変更 | 内容 |
|---|---|---|
| `children` | `birth_date date`(null 可)の列を足す | 子どもの誕生日(§11 D8)。null 可なので、あさノート・よるノートの既存の行・画面には影響しない |

- 共通の表の定義の正は、ルートの `supabase/schema.sql`。**`main` へのマージで本番 DB に自動で反映される**(`db-deploy.yml`)。
- 変えたら `npm run db:types` で、あさノート・よるノートの型(`database.types.ts`)を作り直す(`_db-types-check.yml` が型のずれを検出する)。
- 誕生日は共通の情報なので、あさノート・よるノートでも後から使える(例: 年齢の表示)。ただし MVP では、両アプリの画面は変えない。
- 既存の列の型・制約は変えない。
- **更新の権限を広げる**(§11 D10): `children` の更新(update)の RLS を「登録した人」から「登録した人、または登録した人と同じ家族のメンバー」に変える(読み取りの RLS と同じ条件)。削除は登録した人だけのまま。
  あさノート・よるノートでも、家族の誰でも子どもの名前を直せるようになる。両アプリの子どもの編集画面が「登録した人だけ」を前提にしていないか確かめ、更新履歴に載せる。
- **作品がある子どもは削除できない**(§11 D11): `sakuhin_works.child_id` は `children(id)` への `on delete restrict` にする。
  あさノート・よるノートで子どもを削除しようとして、この制約で失敗したときは「さくひんノートに作品があるため削除できません」と案内する(両アプリの削除の処理とエラーの案内に追加が要る)。
  - 子どもを登録した人のアカウントの削除(`children.created_by` の `on delete cascade`)も、作品があると失敗するようになる。アカウント削除の処理で、先に子どもの所有を家族の別のメンバーへ移すか、作品の扱いを案内するかを実装時に決める(家族を抜けるときの所有の移し替え `transfer_children_on_group_leave` と同じ考え方)。

#### さくひんノート固有の表

表の名前は `sakuhin_` で始める。

| 表 | 主な列 | 内容 |
|---|---|---|
| `sakuhin_child_settings` | `child_id`(`children` への参照・主キー)、`museum_name`(任意) | 館の名前(さくひんノートでしか使わないため、共通の表には置かない) |
| `sakuhin_works` | `id`、`group_id`、`child_id`、`created_by`、`made_on`(制作日)、`title`、`kind`(種類)、`memo`、`frame`(額縁)、`is_featured`(常設展)、`keep_original`(実物保管)、`image_path`、`thumb_path`、`width`、`height`、`created_at`、`updated_at` | 作品 |

- 読み書きは RLS で「同じ家族のメンバー」に限る。子どもの作成者が家族を抜けたときの扱いは、`children` の既存の仕組み(所有の移し替え)に合わせる。

## 10. MVP の対象外

- 子どもの声の録音(作品の説明)
- 作品集の PDF・フォトブック
- 祖父母への共有・おやノートとの連携
- 四隅の自動検出・自動での切り抜き
- AI による自動のタグ付け・タイトル付け
- 1つの作品に複数の写真(立体作品の別アングルなど)
- フォトフレーム(スライドショー)モード
- 「〇年前の今日」の通知などのプッシュ通知
- 作品の検索・タグ
- 端末への画像の保存・SNS への共有

| D6 | 言葉づかい | 収蔵する・〇〇ちゃん美術館・〇〇の部屋・キャプション・常設展。「館長」は使わない(§3) |
| D7 | データベース・ログイン | あさノート・よるノートと同じ Supabase プロジェクトを共有する(§9) |
| D8 | 誕生日の置き場所 | 共通の `children` 表に `birth_date` の列を足す(§9.2) |
| D9 | 補正前の元の写真 | 残さない(§8) |
| D10 | 子どもの情報(誕生日を含む)を編集できる人 | 同じ家族のメンバーなら誰でも。削除は登録した人だけ(§9.2。あさノート・よるノートにも適用) |
| D11 | 作品がある子どもの削除 | できない。あさノート・よるノートでも案内を出して止める(§9.2) |

## 12. 未確定事項

実装に入る前に決める。推奨案は、決まり次第 §11 へ移す。

| # | 事項 | 推奨案 | 主な理由 |
|---|---|---|---|
| A3 | 写真の容量と費用 | Supabase の Storage の容量を、あさノート・よるノートの利用分と合わせて確認する(プランの上限を超える前に分かるようにする) | 写真は数年で数千点になる(§8) |
| B1 | 額縁の種類 | §6.1 の5種類 | 見た目のモックで確かめてから確定する |
| B3 | 通信できないときの閲覧 | 一度見た一覧(サムネイル)は端末内に持つ | あさノート・よるノートはオフラインでも使える。収蔵だけは通信が要る(§7) |
| B4 | 部屋の名前の決まり | §5.4 の表に固定する | 「3歳児クラス」などの呼び方の切り替えは、要望が出てから考える |
| C1 | 家族から抜けた人が収蔵した作品 | 家族に残る(他のメンバーが引き続き見られる) | 家族の美術館の作品なので、収蔵した人ではなく家族のもの |
| C2 | 保存期間 | 設けない。家族のメンバーが削除したときだけ消す | 記念に残すためのアプリなので |
